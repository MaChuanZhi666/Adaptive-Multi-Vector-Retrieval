# 多向量检索索引持久化优化方案

## 学长这句话的意思

当数据规模变大时，全部索引和 embedding 不能都放在内存/GPU 显存里。

所以需要：

- 把索引结构持久化到磁盘；
- 查询时只加载相关部分；
- 避免每次查询都扫大量 embedding；
- 减少磁盘 I/O、CPU 内存占用、GPU 显存占用。

## 可以优化的对象

### 1. IVF posting list

即：

- centroid -> document IDs
- centroid -> token IDs
- centroid -> residual codes

优化方向：

- 按 centroid 分文件；
- 按 shard 分块；
- mmap 读取；
- 热门 centroid cache；
- query 命中的 centroid 才加载。

### 2. Residual / PQ code

即压缩后的 token 向量残差。

优化方向：

- 候选出来后只加载候选文档 residual code；
- 用连续内存布局减少随机读；
- CPU 预取 + GPU 异步拷贝；
- 大文档分块。

### 3. Doclens / metadata

多向量检索需要知道每个文档有多少 token 向量。

优化方向：

- doclens 常驻内存；
- offset array 常驻内存；
- 大 embedding/code 文件落盘。

### 4. Candidate cache

对于高频 query 或相似 query：

- cache top centroid；
- cache candidate IDs；
- cache residual code shard。

## 适合先做的实验

### 实验 A：索引文件结构分析

读取 ColBERT/PLAID index 目录，统计：

- 每个文件大小；
- 哪些文件必须常驻内存；
- 哪些文件可以 mmap；
- 哪些文件按 query 访问。

### 实验 B：候选数量与延迟关系

改变：

- ncells；
- centroid_score_threshold；
- ndocs。

观察：

- candidate_count；
- final_scored_count；
- latency；
- recall。

### 实验 C：模拟落盘

先不改完整系统，只模拟：

- 把某些中间数据放到磁盘；
- 查询时按需读取；
- 记录 I/O 时间。

## 推荐结论

短期选型：

- PLAID：最适合作为 baseline；
- WARP：适合做低延迟/低内存对比；
- IGP：适合做高质量候选生成方向；
- GIGP+：适合后续 CPU/GPU 协同方向。

持久化优先从 PLAID 或 WARP 入手，因为二者都有清晰的 IVF / centroid / compressed-code 结构。
